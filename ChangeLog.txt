=====================================================================
 Win95Doom-remake - Complete Project ChangeLog
 Through 2026-08-22
=====================================================================

A faithful recreation of id Software's DOOM95 (the official Windows
95 port, shipped mid-1996), rebuilt on top of the original DOOM C
source and driven by archaeology of the surviving binaries.

Historical anchors preserved in-tree (files keep their true 1996
mtimes):

    DOOM95.EXE     June   6, 1996      DOOMCFG.DLL  May 28, 1996
    DOOMLNCH.DLL   June   6, 1996     DOOMIPX.DLL  May 29, 1996
    DOOMMDM.DLL    May   29, 1996     DOOMSER.DLL  May 29, 1996
    dpxband.dll    May   15, 1996     <-- matches handshake exp1
                                          constant 0x19960515 exactly

 PHASE 4 - XBAND reverse engineering (2026-08-21, day/evening)
---------------------------------------------------------------------

* Wrote PE analysis tooling: pedasm.py (recursive-descent
  disassembly from entry + exports, then linear sweep),
  dumpfn.py, vsurvey.py.
* Full disassemblies produced: xband docs/dpxband.asm (~1.7 MB)
  and dpmodemx.asm.
* Resource dumps: doom95exe_resource_dump/,
  dpxband_resource_dump/.
* Protocol documented in XBAND_RE_NOTES.md: the game talks to an
  "XBUI" front-end over two anonymous pipes (XBUIREAD/XBUIWRITE
  decimal HANDLE env vars); 16-byte requests {op,a,b,c}, framed
  responses {len,len}{payload}; opcodes INIT(1000)/GETGAMEDATA/
  SENDGAMEDATA/GETPLAYERDATA/SETPLAYERNUM; INIT payload carries a
  16-byte signature ("W95DOOM-XBAND") plus exp1=0x19960515 and
  exp2=2, player count and role.
* RECONSTRUCTION PROJECT xband/:
  - Headers: xband.h, xbandapi.h, dpxband.h (also mirrored into
    win95/include/).
  - xband.c: client library with NATIVE pipe backend and DLL
    backend (LoadLibrary of genuine XBANDAPI.dll, wire format
    verified against XBANDAPI.asm 0x10001450+).
  - dpxband.c/.def/rc: rebuilt DPXBAND.DLL shim.
  - xbui.c: reimplementation of the XBUI front-end - owns UDP,
    spawns the game with inherited pipe handles, relays datagrams.
  - Test suite: apitest, chat, dlltest, dptest + test/e2e.sh;
    chat connect/PING/PONG passed over real UDP loopback.
  - Static archives installed into win95/lib/.

 PHASE 6 - netgame bring-up (2026-08-22, early AM)
---------------------------------------------------------------------

Five stacked bugs found and fixed:

1. WAD-not-found masquerading as a hang: WIN95 branch searches only
   exe-dir/CWD (d_main.c D_SetupWadPaths95), ignores DOOMWADDIR.
2. exp1 mismatch: xbui serves exp1=0x19960515, exp2=2; client sent
   0,0.
3. Stale archive: linked vendored win95/lib copy instead of the
   rebuilt one; win95/lib refreshed.
4. CreateProcess shadowing: xbui launched a stale exe from its own
   application directory first; absolute Z:/ paths + MD5 checks in
   test scripts now.
5. UDP peer discovery deadlock: host drops datagrams until a peer
   is learned while a listening DOOM never sends; explicit --peer
   on both sides.

RESULT: full netgame - host player 1 of 2, guest player 2 of 2,
identical arbitration (startskill 2 startmap 1 startepisode 1),
both rendering E1M1 from different viewpoints with live tics.

Cleanup: debug traces stripped; archives refreshed; solo
regression green (player 1 of 1); DOOM95R.EXE deployed.

 PHASE 7 - linear.asm (2026-08-22, morning)
---------------------------------------------------------------------

* NEW FILE: win95/linear.asm (NASM, -f win32) - recreation of the
  original module (source #54): renderer inner loops, per id's DOS
  tmap.S shipped in README.asm.
* _R_DrawColumn_Asm uses the tmap.S frac<<9 / >>25 precision trick;
  register-based, no self-modifying code, no colormap-alignment
  assumptions.
* BUG CAUGHT vs reference: tmap.S packs span position/step and
  drops the six lowest fraction bits of each component, shifting
  single texels on longer spans. Our span routine advances full
  32-bit fractions instead.
* PROOF: harness linking both implementations side by side over
  20,000 seeded-random cases - byte-exact everywhere, including
  wrap-around and negative-count early returns.
* Hooked via existing colfunc/spanfunc pointers under -DUSEASM in
  r_main.c; fuzz/translated/low-detail variants remain C.
* Makefile gained the NASM rule and obj/linear.o.
* In-game A/B identical beyond animation noise. Deployed.

 PHASE 10 - dither.c / dither.h (2026-08-22, late afternoon)
---------------------------------------------------------------------

* NEW FILES: win95/dither.c, win95/dither.h (original source #3):
  ordered-dither quantization for restrictive desktop depths.
* 4x4 Bayer matrix; Dither_Update caches tables keyed on palette +
  channel maxes/shifts; Dither_Table16 (256x16 phases for crushing
  formats) and Dither_Table32 (exact identity LUT for truecolor).
* CopyToSurface integration: >=24bpp path now a single LUT lookup
  per pixel; <=16bpp picks table[index*16 + ((y&3)*4)+(x&3)],
  blending quantization error spatially.
* Header kept windows.h-clean (unsigned char prototype); the 33
  doomtype.h macro warnings in i_w95gdk.cpp confirmed PRE-EXISTING
  by include A/B.
* Host unit tests all pass: endpoints exact in every phase, levels
  always floor or ceil of exact scale, outputs in range, cache
  invalidation works.
* In-game A/B at desktop depth vs previous binary: animation noise
  only. Deployed.

 PHASE 12 - wadread.c (2026-08-22, evening)
---------------------------------------------------------------------

* NEW FILES: win95/wadread.c, win/wadread.h (original source #47):
  standalone WAD file reader - the tool-era grab-bag sibling of
  dutils.c.  Nothing in the game calls it; community analyses file
  the original under redundant ghost code, and this recreation
  ships in exactly that spirit: linked in, minding its own
  business.
* API (wadread_* prefix, no collision with w_wad's W_*): open /
  close with full directory load, numlumps, case-insensitive
  findlump (backward scan like the engine), lumpsize, readlump,
  and an extract() find+allocate+read convenience.
* VERIFIED against the real retail IWAD (2,306 lumps): PLAYPAL
  extracted at its directory-record size (10,752 bytes = 14 x
  768-palette), E1M1 correctly reported as a zero-byte map marker,
  THINGS non-empty, bogus lookups return -1, close resets state -
  all host-side tests passed.
* Makefile.w95: obj/wadread.o after w_wad.o.
* Solo boot regression green.
